# Interactive terminals and desktop maintenance

Owner terminals use `portable-pty` 0.9: ConPTY on Windows and native PTYs on Unix. The UI uses xterm.js 6 and its fit addon. These are real interactive shells with raw UTF-8 input, terminal control sequences, resize, PID/state, tabs and output cursors. No one-shot command runner is presented as a terminal.

The terminal routes are under `/api/v2/orders/{order}/terminals` and require the installation-owner bearer and allowed Origin. They do not accept actor sessions. Actor-private sandbox terminals remain a separate authority. The shell must be a configured `powershell`, `bash` or `sh` executable; shell arguments are fixed. Preview exposes the exact executable, managed chat tool workspace and host permission boundary. An approved digest and original idempotency key are required before process creation. The working directory does not sandbox the host filesystem. Interactive shells inherit only the toolbox's approved environment and named OS user/profile/path variables, never all daemon environment variables or provider keys.

A private write-ahead launch receipt is synced before spawning. Repeated launch requests return the original session. The terminal list shows active tabs and up to128 recent sessions; exact older receipts remain addressable by their original request key. Old receipts after daemon restart return `interrupted` and never reattach a stored PID or replay commands. The process remains live when its UI disconnects. Output reconnects by byte cursor from a bounded 1 MiB host buffer; truncation is explicit. Input uses a monotone sequence and exact last-input comparison: ambiguous OS writes are retained, never resent physically. Stop closes the exact PTY and its attached process group. The last active terminal tab releases its managed tool-workspace lease so ordinary jobs can use that workspace again.

The existing `terminal_persistence_mode` controls device behavior: `runtime` uses only live host sessions; `scrollback` explicitly stores at most 64 KiB of output and its cursor on this browser/device; `restore-tabs` restores tab selection/closed-tab state. None starts a process after daemon restart. Terminal input is never written to the launch journal. Saved output can contain sensitive text and is described accordingly in Settings.

The native updater reports active owner PTYs and rejects shutdown until the user explicitly stops them. Backup maintenance participates in the same lifecycle admission lock. Cancellable finite downloads preserve Content-Length so truncation or checksum mismatch is detected by the receiver.

The guarded native desktop commands provide actual OS autostart status/enable/disable, native notifications and sound. Installing or starting the application never enables autostart. The setting changes the OS registration only after its explicit UI action; any discrepancy between actual OS state and saved preference remains visible. Native notifications use the Tauri notification plugin; Windows sound uses MessageBeep, macOS its system sound and Linux an installed canberra-gtk-play. Browser feedback uses Notification and Web Audio with their platform permissions. Completion notifications currently require an open application window.

The daemon reads existing owner preferences every minute: `auto_backup_db`, `db_backup_interval_hours`, `chat_retention_days`, and `db_cleanup_on_start`. SQLite uses SQLite's transactionally consistent `VACUUM INTO` image, including committed WAL changes. PostgreSQL uses an administrator-selected absolute `COWORK_PG_DUMP` program and custom-format dump; database passwords are passed through the child environment, not arguments or diagnostic output. The UI reports capability availability before offering automatic backups.

Backups are private database images in the data directory's `database-backups` folder. Only generated UUID files with a matching owned manifest, size and SHA256 are eligible for automatic pruning; unrelated files are preserved. The latest seven images are retained. Retired metadata receipts survive image removal so replaying an old manual request returns its original acknowledgement. Downloads verify bytes and expose the same integrity headers as existing verified downloads. Database images include stored encrypted references; external workspace files and decryption keys need their separate backup procedures. Restore must occur with the daemon stopped and the matching keys/data available; no automatic restore overwrites a running installation.

Retention archives at most 1,000 inactive owner chats per tick, scanning beyond protected chats. It acquires each candidate's actual toolbox workspace lease and retains the leases through database commit, skipping active PTYs and jobs without a check/start race. It preserves drafts, active runs, task/schedule chats, and all immutable history/audit evidence. Actor/private and team histories are unaffected. It is an archival policy, not secure erasure. SQLite/PostgreSQL transactions recheck current order state while holding the appropriate admission locks.

Sources: [portable-pty](https://docs.rs/portable-pty/0.9.0/portable_pty/), [xterm.js](https://xtermjs.org/docs/guides/using-addons/), [Windows pseudoconsole lifecycle](https://learn.microsoft.com/en-us/windows/console/creating-a-pseudoconsole-session), [Tauri autostart](https://v2.tauri.app/plugin/autostart/), [Tauri notifications](https://v2.tauri.app/plugin/notification/).


Connector management uses a bundled Python stdlib MCP adapter. Each connector revision publishes one immutable factory/catalog and one atomic encrypted environment value containing the URL (including private paths/queries), optional bearer and public operation binding. The metadata, run bindings, catalog and browser recovery journal contain no secret URL or key. URL and key configuration together are bounded to 2,000 bytes; keys are at most 512 ASCII bytes. HTTPS and explicit loopback-IP HTTP are supported. User information and fragments are rejected. Native writes retain their separate authority and native save confirmation; a server owner browser cannot use native key custody.

The `send_json` tool includes the frozen destination origin as a required constant argument visible in approval, together with the concrete JSON payload. It performs exactly one POST without proxies, redirects or retries. It returns status and public origin, excluding remote response bodies/headers that may echo webhook secrets. A delivery failure closes the transport without an acknowledgement; MCP retains the uncertain-effect checkpoint. A connection test performs only HEAD; HTTP status (including 405 for a service that disallows HEAD) is shown explicitly. Saving/discovering a connector sends no message.

Editing creates a new MCP server/factory version and keeps the prior accepted binding and encrypted URL/key intact. Only the latest enabled connector is available for a new selection. Managed connector factories cannot be modified through generic MCP forms. Disabling blocks all historical factories; re-enabling creates another version. Deleting revokes all bridge/environment credentials and stops every known connector connection. An immutable old request receipt may still return its original acknowledgement after deletion, but cannot re-enable it.

The existing MCP preferences have actual effects: automatic reconnect makes at most three attempts at a NEW initialize/catalog handshake, before dispatch. Catalog mismatch, invalid protocol/schema and configuration errors are not retried. Resumed/busy/uncertain sessions and tools/call are never replaced or replayed. Verbose diagnostics log only lifecycle phase, server ID, attempt and fixed error code. The environment-editor and manual-catalog preferences control their real owner UI editors; they are display preferences, not a substitute for owner API authorization. Existing encrypted environments continue working when their editor is hidden.


Backup saving has its own streaming path up to 1 TiB, independent of the unchanged 64 MiB ordinary file/tool cap. Native IPC accepts only a known local backup UUID plus expected manifest length/SHA256, verifies the current owner manifest, downloads the fixed loopback route into a private temporary file with incremental SHA256, and uses the broker's pinned-directory/permission-preserving atomic save after a user-controlled dialog. Temporary and staged files are removed on failure; no live application data can be overwritten through this save action. Existing/changed destination checks remain in force, with bounded streaming hashes rather than whole-file allocations.

A server browser can save larger images through an available user-selected File System Access writable stream. The sink is closed/published only after exact length and incremental SHA256 match; truncation, corruption or altered headers abort the uncommitted stream. Browsers without file streaming retain the ordinary bounded small-download fallback and show a clear message for larger images. No temporary public URL or query token is created. Streaming hashes use pinned [noble-hashes 2.0.1](https://github.com/paulmillr/noble-hashes/tree/2.0.1); the write/close boundary follows the [File System Standard](https://fs.spec.whatwg.org/#api-filesystemfilehandle-createwritable).

Codex account create/edit/login/logout/delete now use strictly validated, secret-free persistent mutation references scoped to endpoint and installation-owner/actor identity. Session-token rotation preserves the same reference; an incomplete actor context cannot fall back to owner credentials. Explicit reconciliation repeats the original body/key/revision. Login URLs and device codes are never written to the browser request journal. Damaged references remain blocked until explicit local discard and authenticated state reload.

Chat deletion is a distinct permanent live-workspace tombstone (migration 0098), separate from reversible archival. The owner CAS/idempotent action removes the chat from active, archived and search listings; it archives linked tasks and pauses schedules in the same transaction. Active runs, claimed schedule occurrences, native jobs or PTYs block deletion. Native process/file/browser admissions hold workspace custody while rechecking live chat state, so deletion cannot race a fresh host effect. Immutable original acknowledgements remain acknowledgements only; historical messages, run events, artifacts and export/audit records remain available. A deleted chat cannot be restored, renamed/moved, edited, branched, or receive new runs/tasks/schedules; retention and project retirement do not revive or move its tombstone.
