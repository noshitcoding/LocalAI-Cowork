## Compilation and frozen inputs

Definitions contain named roles, explicit provider IDs/revisions, goals,
dependencies, budgets and opaque tool/folder references. Compilation rejects
missing or duplicate roles/providers/nodes/dependencies, dependency cycles, reserved child
IDs, stale provider revisions, unavailable credentials, invalid context limits
and unsupported delegation configurations. It freezes only explicitly referenced
provider profiles, without fallback. Sequential mode adds ordered dependencies;
parallel mode preserves the dependency graph; hierarchical mode additionally
permits bounded delegation to named role templates.

Effective rights are the intersection of the trusted application scope, workflow,
role and node. A child additionally intersects its parent's rights with its role
and requested rights. Tool/folder references are opaque identifiers, not validated
host paths. Their presence does not authorize IO. The application must obtain the
scope from current policy and continue enforcing exact approvals, canonical paths,
credentials and revocation through existing brokers. The reducer does not replace
any of those checks. A checkpoint hash is an integrity check, not a signature or
proof of authorization.

## Scheduling and accounting

A pending node becomes ready after every dependency has completed. Active claims
cannot exceed the lesser of the workflow and trusted-scope parallel limits.
Delegating parents release their slot while waiting for all children. Resumption
issues a new claim token; the old token cannot complete or admit another action.
Depth, total delegation and total node limits are checked before any mutation is
published. `continue_independent` blocks dependents, waiting parents and pending
descendants of a blocked parent. `stop` also prevents new actions in already
claimed independent nodes; previously admitted receipts may still settle.

Each action admission consumes one step. Model admissions reserve the full frozen
provider context window. All concurrent agents use one shared token/step pool;
children also consume every ancestor's pool, so delegation cannot multiply the
parent's allocation. Fully reported usage settles to measured input plus output.
Incomplete usage retains at least the full reservation. Reported context/output
overruns interrupt the workflow before another action is admitted.

Caller timestamps are Unix seconds. Time checks retain the first workflow and node claim times, including waits and
parent resumption. Descendants inherit ancestor deadlines. Clock rollback rejects
a new mutation. These are per-workflow pools; organization/device/offline reservations remain separate unfinished services.

The reducer uses a durable wall-clock check. The native model adapter additionally
sets a monotonic request deadline from the remaining parent/node/ancestor limits,
checks the live lease and parent state while streaming, and stops the HTTP request
on cancellation or expiry. Already admitted work may settle after a deadline so
its evidence is retained. Artifact approvals additionally recheck parent, node and
ancestor deadlines before a new decision/effect commits. Complete workflow
cancellation acknowledgements, expiry and external tool/process orchestration
remain to be integrated.

## Checkpoints, idempotency and conservative recovery

Every accepted mutation appends a decision and increments the checkpoint revision.
Expected-revision mismatch rejects a new operation. Failed multi-child delegation,
denied rights and exhausted admission do not partially modify the checkpoint.
Validation replays the complete bounded decision history from the compiled plan
and compares reconstructed state; forged node rights, counters and output hashes
cannot bypass replay validation.

Admission IDs bind to the exact claim and normalized operation digests. Exact
replays return the saved receipt with no additional dispatch permit and no extra
budget charge. Changed arguments/claims conflict. The one-shot permit is neither
cloneable nor deserializable. The caller must durably compare-and-swap the checkpoint
before consuming it and performing IO; in-memory possession is not enough.

Coordinator recovery interrupts active claims and preserves their unresolved
admissions and reservations. No submitted model or uncertain external effect is
automatically repeated. Database-only artifact transactions may retry a known
revision conflict without external IO. An uncertain
tool result interrupts the graph; other admitted results may settle, but new actions
are refused. Explicit resume can now retry result/snapshot finalization only when
the whole graph is already terminal and has no pending or uncertain attempts.
Reconciliation and general safe resumption of interrupted agents remain unfinished. Domain tests serialize and re-open the reducer;
storage tests separately verify database transactions and hard process death.

## Durable registry and run transaction

Migration 16 adds project-scoped workflow heads, immutable definition versions,
publication/revocation receipts and run checkpoints. A definition may be saved
without an available model. Starting a run rechecks the exact definition,
provider revisions and credential-ready status, compiles the plan, clips budgets
and freezes a `RunSpec.workflow` binding. This occurs in the transaction that
consumes the order revision and inserts the initial message/events. A failed
compilation leaves the order, draft and messages unchanged. The private model
adapter resolves the exact configured profile and native environment credential
before admission and again before sending; a missing, changed or invalid profile
never chooses a replacement. Model catalogue reachability and current policy
preflight still require the trusted product application service.

Create and publish use idempotency keys and body hashes. Changed replays conflict;
exact receipts do not publish a second version or reactivate a revoked workflow.
Concurrent publishers serialize on the head and still compare the expected
revision. Revocation is terminal. Queued runs with new work cannot start after revocation;
new claims/admissions/delegations on active runs also recheck it. Results of
already admitted work may settle so their evidence is retained. Explicit
completion-only retries on a fully terminal graph do not contact a provider or
create new execution rights, and remain possible after library revocation.

A workflow command stages a replay-validated next checkpoint. Its transaction
checks the parent worker lease, immutable plan, expected checkpoint revision and
hash, then commits the parent record, checkpoint, aggregate model budget/usage
and monotone run event sequence together. A new one-shot dispatch permit is
returned only after commit. A trigger-induced event failure rolls everything
back and returns no permit. Exact admission/settlement replays return a read
receipt; they may use an old lease but never grant new IO. SQLite lock contention
retries only the pure transaction. Before commit, storage rechecks both an original
worker lease and a newly minted claim lease after any lock wait. A PostgreSQL head
lock that outlasts the new lease must leave the parent queued with no start event,
claim or execution permission. No external action is performed inside retries.

Expired parent lease recovery interrupts active node claims and retains every
unresolved attempt/reservation. Pending or uncertain actions prevent terminal
cancellation and general agent resume remains unavailable. One synthetic child actor
writes a disposable fixture file after admission; killing its process before
settlement preserves the checkpoint on reopen and produces no second permit.
This proves SQLite crash durability of admission/checkpoint state, not a real
workflow broker, sandbox, power-loss durability or machine reboot.

Order export format 12 includes full frozen workflow plans, progress, agent seeds,
requests and responses with binding/progress/response hashes; the outer export
hash covers them, including optional human_inputs and owner-scoped draft/snapshot/intent
records. Verified imports are archives, never new execution rights. Old `RunSpec` JSON
without a workflow and old archives without workflow snapshots remain readable.
Schema 7 keeps the event wire shape; human input uses additive event kinds. Workflow
format 3 adds replay-bound input checkpoints/answer evidence to the format-2 confirmed
tool receipts and atomic decisions; the reader accepts formats 1 and 2. This additive read compatibility does not promise that older
binaries can read new tool histories. These private JSON snapshot bodies are validated
on export and are never accepted as authorization or as an import/resume API.
The public run view exposes the frozen binding, roles, node/accounting status, exact
actionable approvals, scoped human questions/receipts and distinct blocked resume flags.
Private leases/plans/permits remain outside that view; full enterprise monitoring is open.

## Durable per-agent requests and confirmed answers

Each agent gets its own immutable seed, role instructions, the order conversation
and completed direct dependency results. Parent system metadata is removed; a
fresh capability frame lists only that node's intersected folder references. Role
instructions and folder system frames are validated on checkpoint read. Independent
agents do not inherit siblings' model history. Completed direct delegated-child
results are captured per request; later children do not rewrite old requests.
Files, dependency output and model-proposed tool calls are data, never new rights.

A model turn freezes its scoped RunSpec, exact messages, catalogue, logical request
hash and node claim. Request admission, reservation and agent checkpoint commit
together before a non-cloneable/non-deserializable send permit is returned. Final
dispatch checks the saved turn, live parent lease, workflow revocation and the
runtime's exact catalogue. The adapter never performs external IO inside a CAS
retry. Concurrent agents may retry the pure admission/answer transaction only.

The complete model answer, proposed tools, reported usage and body hash are saved
with settlement and the parent event/accounting in one transaction. The reducer's
settlement receipt also binds that response hash, so changing an answer and merely
rehashing its journal body fails validation. A completed node must use the exact
last accepted tool-free answer. Duplicate calls read confirmed answers without
provider IO; pending duplicates return an uncertain-result error and cannot cancel
the original sender. Lost/truncated responses, failed commits and expired senders
retain their unknown reservation and interrupt the parent; no model is sent again
automatically. Recovery/resume must eventually distinguish explicit evidence from
assumptions about a remote request's outcome.

Responses are bounded by content, tool-count and serialized-size limits. Raw tool
IDs are unique within one response and names must belong to the advertised node
catalogue. Rejected proposals retain their response and usage but cannot complete
the node or grant IO. The low-level adapter leaves valid proposals pending. The
coordinator now handles the three database-only artifact tools and scoped request_input;
other valid tool kinds still cause a known unsupported-tool node failure without
performing them. Repeated raw IDs in later model turns are allowed and receive
different durable broker identities.
The full stored workflow body is limited to 32 MiB before admission/settlement.
Context size still uses the existing conservative byte-based estimate; qualified
tokenization, compaction and structured output schema checks are unfinished.

Thirteen private runtime scenarios use the actual loopback HTTP/SSE transport:
two provider requests overlap, dependencies receive confirmed results, duplicate
requests do not resend, output overruns/invalid proposals retain evidence, deadline
and truncated-stream failures hold reservations, failed commits stay unknown,
profile changes cannot fall back, body tampering fails the accounting receipt,
and a confirmed answer survives hard child-process death even when its HTTP server
and provider configuration are gone. These are synthetic providers, not real LLM,
OS-reboot, workflow tool/sandbox or complete daemon-worker acceptance.

## Private automatic graph coordinator and durable parent completion

`Runtime::run_native_workflow` is a trusted Rust application entry point, not a
public API. It takes one queued parent's durable lease before scheduling. A duplicate
controller cannot inherit that lease, send another request or interrupt its owner.
Confirmed terminal calls return a read receipt even with no configured provider.
The ordinary daemon worker now has a separate internal entry for an already
claimed parent. It uses the exact queue-issued lease and folder ownership rather
than claiming the parent again. Product start/preflight and explicit workflow selection now use this same queue/coordinator.
External workflow brokers remain unavailable.

The controller launches ready nodes up to the frozen parallel limit. It accounts
for a spawned sender's full context window until that same reservation appears in
the shared durable checkpoint. When temporary reservations fill the pool, other
nodes wait for settlement rather than fail solely because another agent is active.
Dependencies receive confirmed node outputs. Sequential graphs cannot overlap.
CAS retries concern only claims/known results, never provider IO. A readiness change
caused by a parallel failure rechecks the graph before claiming a stale entry.

Pre-admission errors become known node failures with no remote request. Rejected
or unsupported external-tool proposals preserve their complete response/usage and
fail the node without that tool effect. Known database-tool budget exhaustion fails
that node; an independent already admitted model can still settle its answer.
The reducer applies stop/independent failure rules; completed independent outputs remain available after failure. An unconfirmed
request instead interrupts the parent and retains every unresolved reservation.
Cancellation/shutdown stops owned tasks and uses conservative interruption when
remote outcome or usage is unknown; complete cancellation/evidence orchestration
is still unfinished.

Parent completion is derived inside the locked run transaction from the validated
terminal graph. A premature generic `Completed` transition is denied. Success
shows terminal root outputs; failure preserves completed root outputs. Intermediate
and child data remains in the exported checkpoint. The result, parent state, lease
release, conversation message and sequenced finish events commit together. Exact
terminal repeats insert no second message/event. No additional summarizer/provider
request is made merely to finish the conversation.

Managed workspaces use the existing persisted snapshot phase. The final text is
checkpointed before snapshot IO; `Completed` requires its confirmed manifest.
Snapshot failure keeps writer ownership and the pending final text. An explicit
resume of a fully terminal graph retries only result/snapshot finalization, with
no model configured and no model replay. General interrupted graphs still require
future evidence reconciliation and safe node/claim recovery.

Twelve additional coordinator scenarios cover sequential/parallel order, a pool
that fits only one context window, rejected-dependency independent results, stop
before admission, duplicate ownership, failed result commit with explicit
completion-only retry after template revocation, conservative in-flight shutdown,
unsupported proposals without effects, real broker snapshots/writer release,

The provider/process actors are disposable deterministic fixtures. Real LLM and

## Private database-only artifact broker and exact approvals

`crates/storage/src/workflows/tools.rs` executes only `create_artifact`,
`list_artifacts` and `read_artifact`. It accepts saved model-turn/raw-call identities,
never replacement caller arguments. The shared policy evaluator receives that
node's frozen scoped `RunSpec` and the existing exact approval records. Read-only
mode, deny precedence and the configured confirmation mode retain their meaning;
a model response or opaque reference cannot grant rights.

A durable broker ID is the canonical SHA-256 of a domain-separated object containing
run, node, model turn and raw provider call ID. Parallel agents and later turns may
therefore reuse `call-1` without sharing an approval or receipt. Provider messages
retain the original raw ID. Approvals bind the broker ID, exact saved name and
arguments, execution target, policy revision and scoped approval fingerprint.
Request, resolution and effect have separate checked `ToolGate` paths. A changed
fingerprint or changed decision conflicts. Approval resolution is not execution
permission by itself: effect commit rechecks template revocation, live parent lease,
active node claim, current policy and parent/node/ancestor deadlines. Those time
limits are checked before requesting a first approval or returning an existing
pending approval, after the workflow head lock and immediately before transaction
commit. An approval wait cannot extend a node or ancestor deadline.

A pending artifact approval leaves the parent `Running` under its existing lease.
The coordinator continues heartbeat and independent sibling model work while that
node waits. This is a private node-level wait, not a new public workflow-state or
selection contract. Revocation, shutdown or cancellation prevents additional
unapproved work; unresolved external model reservations remain conservative. Under
`stop`, a known sibling failure rejects further tool/approval activity as the known
node error `workflow_stopped`. The stop guard runs before the operation and again
after the workflow head lock. The final commit separately fences the original
lease and deadline; no separate final stop check is claimed. The guard creates no
new sibling approval and does not turn a previously confirmed sibling answer into
an unknown request. Already admitted
model answers may still settle so their evidence remains available.

For these database-only tools, admission and settlement form one replayable
`ToolResult` reducer decision, increasing the checkpoint revision once and consuming
one step without a token reservation. Artifact content/index, exact receipt and
result hash, workflow checkpoint, parent accounting and sequenced events commit in
one database transaction. A failed commit leaves none of that tool effect, receipt
or charge. Exact receipt replay creates no second artifact, event or step. It may
read already confirmed data with an old lease but grants no new execution rights.
Policy denial or invalid/missing artifact arguments produce confirmed error replies
without an artifact effect. A known tool `BudgetExceeded` instead fails the node,
allowing independent already admitted model answers to settle according to the
workflow failure policy.

The explicit artifact read capability covers immutable outputs of the authorized
order, including earlier runs, plus its verified inherited branch snapshot. Reads
check artifact metadata against the database index, the source-run/parent-order
binding, content size/hash and the inherited snapshot integrity. An inherited
artifact retains its original source identity; this explicit branch inheritance
does not authorize arbitrary foreign-order IDs. This scope provides order-level
result access, without host-file, MCP-resource or arbitrary project access.

Agent contexts append the saved assistant tool calls followed by confirmed tool
replies in proposal order, using raw provider IDs. Another model turn is constructed
only after every proposed call has a receipt. Each continuation receives a new
admission/request identity and reserves its frozen model context again. It waits
only while still-unconfirmed sibling model reservations can recover enough shared
capacity; irrevocably charged usage, exhausted steps or deadlines cause a known
pre-admission failure rather than an indefinite wait or a repeated provider request.

## Shared worker queue and start revocation

`Store::claim_for_worker` scans the durable queue for both ordinary runs and trusted
workflow runs. `Runtime::serve` routes a workflow parent to
`execute_claimed_workflow`, passing its already committed lease and workspace
ownership. One parent occupies one supervisor worker slot; its coordinator owns
bounded child tasks. The older `Store::claim` remains single-agent-only and
excludes workflow checkpoint rows. Two supervisors cannot dispatch the same
workflow parent. A workflow checkpoint whose parent binding is missing is rejected
rather than falling through to single-agent execution.

Start checks cover both `Queued` and `WaitingForExecutor`. Workspace contention
leaves a run waiting without a start time or model admission. If the exact template
is revoked before the run has started, the typed `workflow_revoked` denial closes
that parent as `Failed` and records one `workflow_start_rejected` event. The closure
revalidates revocation in the run transaction and permits only an untouched `Ready`
graph at revision zero, without attempts or agent journals. It does not fabricate a
failed graph or an assistant result. Exact terminal reads preserve that record.
Other integrity, permission or storage errors cannot use this exception. The queue
continues scanning after a safely closed start rejection, so a later ordinary run
can still execute.

Once active, cancellation or supervisor shutdown stops the coordinator's owned
model tasks. An uncertain remote outcome leaves the parent `Interrupted` and keeps
its complete token reservations; restart does not resend those requests. An explicit
resume is supported only for a fully terminal graph without unresolved attempts.
That completion-only run can return through the shared queue after template
revocation and with no configured provider, because it finalizes already confirmed
results and performs no new model action.

Eight new runtime scenarios exercise the ordinary `Runtime::serve` path: workflow
and ordinary work with one parent slot, competing supervisors, real workspace
contention followed by snapshots, revoked waiting work followed by a successful
ordinary run, durable cancellation and reopen without replay, supervisor shutdown,
explicit completion-only queue recovery after revocation, and hard worker-process
death with unknown requests. The hard-kill fixture uses the actual supervisor for
recovery; it shortens only its own remaining lease wait after the child is killed.
The shared SQLite/PostgreSQL workflow contract additionally exercises queue claim
exclusivity, workspace waiting and exact revoked-before-start closure. A separate
storage case rejects a missing parent workflow binding. A PostgreSQL case holds an
